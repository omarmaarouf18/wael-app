## 1. What changed in code

### 1.1 New routes

| Route | Handler | Notes |
|---|---|---|
| `POST /academy/orders` | `CreateOrder` | Web-only cart checkout, 1-50 subjects, all-or-none. |
| `GET /academy/me/orders` | `GetMyOrders` | Student's orders, newest first. |
| `GET /academy/me/orders/{id}` | `GetMyOrderByID` | IDOR-safe 404 for another student's order. |
| `GET /internal/admin/request-groups` | `AdminRequestGroups` | Grouped pending read model (student → order → items). |
| `POST /internal/admin/requests/bulk` | `BulkRequests` | Per-id accept/reject results, no silent partial failure. |

Existing `POST /academy/subjects/{id}/purchase-request` now creates a web
order of one behind the same response shape. `POST
/academy/subjects/{id}/access-request` (the app) attaches its request to the
student's open `app` order; its request/response body is unchanged.

### 1.2 Data model

- New `orders` collection: `_id`, `user_id`, `source` (`web`|`app`),
  `status` (`open`|`closed`), `payment_method`, `transfer_reference`,
  `normalized_reference`, `sender_number`, `amount_paid`, `created_at`,
  `closed_at`.
- `purchase_requests` gains `order_id` (server-side; not exposed by the app
  response).
- Indexes: unique partial `orders(user_id)` where `source="app"` and
  `status="open"` (one open app order per student); unique partial
  `orders(normalized_reference)` where non-empty; `orders(user_id, created_at)`;
  `purchase_requests(order_id)`.

`payment_records` is unchanged: one append-only row per granted subject with
`price_at_grant`. The typed transfer amount lives on the order only
(`amount_paid`); cart request rows keep their subject price so the legacy admin
queue's per-item amount check stays meaningful.

### 1.3 Mongo standalone / all-or-none

Mongo is standalone (SPEC R4), so there is no multi-document transaction. Web
checkout inserts the order first, then its requests, and on any failure runs a
compensating delete (`purchase_requests` by `order_id`, then the order). The
MemoryStore validates every row before appending anything. The unique partial
indexes are the final guard for concurrent duplicate references and duplicate
pending requests.

### 1.4 Legacy migration

`NewMongoStore` runs an idempotent `MigrateLegacyAppRequests` after index
creation: existing **pending** app/mobile requests with no `order_id` are
grouped into one open `app` order per student (order `created_at` = earliest
request). **Accepted/rejected history keeps no order** (`order_id` stays
empty); it is not needed for the pending console view and the student order
list only exposes orders created from the migration onward. Rows that already
carry an `order_id` are skipped on every later start.

### 1.5 Concurrent app requests

Two app requests from the same student at the same moment end in one open app
order. The unique partial index on `orders(user_id)` where `source="app"` and
`status="open"` makes the loser of an insert race re-read the winner's order.
Proved by `TestOrders_ParallelAppRequestsOneOpenOrder` (MemoryStore) and
`TestMongoStore_AppOrdersParallelAndMigration` (Mongo, skipped when
`MONGO_URI` is empty).

### 1.6 Bulk audit

Each affected request gets its own `request_accept` / `request_reject` audit
entry. Each bulk call also writes one summary entry:
`request_bulk_accept` / `request_bulk_reject`, `target_type: "request_bulk"`,
`target_id` = first id, detail `count=<n> ids=<comma-separated ids>`. The actor
is the verified admin of the bulk call.

### 1.7 Orphan web order cleanup (no-transaction path)

Because Mongo is standalone (SPEC R4), checkout compensates manually instead of
using a transaction. A crash between the order insert and the request insert can
still leave a `web` order with no requests. The service therefore sweeps them:

- at startup, and every 10 minutes afterwards (`orphanWebOrderInterval`);
- only `source="web"` orders with **no** purchase request row are removed, and
  only when they are older than 5 minutes (`orphanWebOrderAge`), so an in-flight
  checkout is never touched;
- app orders are never removed, and a web order that has requests is kept;
- each removal is logged:
  `[ACADEMY] removed N orphan web order(s) older than 5m0s with no requests`;
- a cleanup failure is logged as a warning and never stops the service.

The store method is `DeleteOrphanWebOrders(ctx, before) (int, error)` on both
MemoryStore and MongoStore. Proved by `TestMemoryStore_DeleteOrphanWebOrders`,
`TestMongoStore_DeleteOrphanWebOrders` and
`TestCleanupOrphanWebOrders_RemovesAndLogs`.

### 1.8 Startup logs

The startup migration now logs what it did:
`[ACADEMY] orders migration: attached N legacy pending app request(s) for M
student(s) to open app orders`. A second start with the same data logs nothing
(the migration is idempotent), which is the operational signal that the data is
already grouped.
